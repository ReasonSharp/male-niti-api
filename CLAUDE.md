# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An Express API for the Male Niti website. It backs the site's dynamic content (services, pricing, portfolio/work, blog, contact form — see `api-spec.yaml` for the full OpenAPI contract) and also renders quote images on demand. `server.js` only wires middleware and mounts routers; each resource's logic lives in its own file under `routes/`.

`services`, `pricing`, `work`, and `blog` expose full write endpoints (`POST`/`PUT`/`PATCH`/`DELETE`) for content management, restricted to a super admin. `contact` additionally exposes `GET /` and `PATCH /:id` (mark `completed`), also super-admin-only; its `POST /` stays public and is the only contact-facing method open to anonymous callers. All of this, plus `/v1/quotable` and the `/api-keys` endpoints, is documented in `api-spec.yaml`.

Also hosts, under `/atodo/v1`, a from-scratch backend implementation of a *second*, unrelated API — the contract for the separate `atodo` (A-To-Do) client project's multi-tenant to-do list app. It has its own auth scheme (per-account JWTs, not the CMS's API keys), its own OpenAPI doc (`atodo-api-spec.yaml`, copied from that project), and its own tables (`db/atodo-schema.sql`) — see "A-To-Do integration" below. Stripe and outbound email are both mocked there (see that section) rather than genuinely wired up.

## Commands

```bash
npm install          # install deps (requires native build toolchain for `canvas`, see below)
npm run dev           # start with nodemon (auto-restart)
npm run prod          # same as dev — nodemon is used in both scripts
```

There is no build step, linter, or test suite configured. **This repo does not run its own Postgres** — it's built to be composed alongside a database (and other services) by another project, which is also responsible for applying `db/schema.sql` **and** `db/atodo-schema.sql` (see "A-To-Do integration" below — two separate files, both need applying). The `pg` Pool connects lazily, so the server itself starts fine without a reachable database, but essentially every route fails until one is reachable — see the note in "Auth, rate limiting, and IP bans" below about `checkBanned` in particular, since that makes even DB-independent routes (like `/v1/api-docs`) fail closed without a database.

### Docker

```bash
docker build . -t mnapi
docker run -v "/your/image/output/directory:/public/out:rw" --network your-network -p "50000:50000" --restart unless-stopped -d mnapi
```

Postgres must already be reachable on `your-network`, with `.env`'s `PGHOST`/`PGPORT`/`PGDATABASE`/`PGUSER`/`PGPASSWORD` pointing at it (baked in at build time, since `.env` is `COPY`'d into the image — see Configuration below).

The Dockerfile is a two-stage alpine build: the first stage installs native build deps (`make g++ jpeg-dev cairo-dev giflib-dev pango-dev libtool autoconf automake`) needed to compile `canvas` from source via `npm ci --build-from-source`. The runtime stage is a **separate, fresh alpine image** — it must independently install the non-`-dev` runtime libs (`cairo jpeg giflib pango`), since only compiled `node_modules` are copied over from the build stage, not shared libraries. If `libcairo.so.2`-style dlopen errors come back, this is the first place to check. It then copies `server.js`, `routes/`, `db/`, `lib/`, the `.env` file, `api-spec.yaml`/`atodo-api-spec.yaml`, and the `.ttf` fonts, and runs as a non-root `appuser`. There is no `VOLUME` declaration on `/api` — a prior version had one, which caused Docker Compose to silently carry a stale anonymous volume across `--build` recreates, shadowing freshly built code with old files. If code changes ever don't seem to take effect after a rebuild, check for a reintroduced `VOLUME` on a directory the image also writes to.

## Configuration

- `.env` is loaded via `dotenv` and is copied into the Docker image directly at build time. It was **tracked in git** for a while (see commit `5c25825`, ".env.template -> .env", and commit `40ab185`, "unignore .env") but is gitignored again as of the A-To-Do integration — don't re-add it to the repo; each deployment is expected to supply its own local `.env` (or a rendered `platform-integration/config.template`, see below). The `PGPASSWORD`/`ATODO_JWT_SECRET` values in the local `.env` are dev-only placeholders — rotate them before any real deployment.
- `ATODO_JWT_SECRET` — HMAC key for signing/verifying the A-To-Do integration's bearer tokens (`lib/atodo/jwt.js`). Also a dev-only placeholder in `.env` — rotate before any real deployment, and treat rotating it as invalidating every currently-issued token (every logged-in atodo session), same as it would for a real JWT secret.
- `MNAPI_OUTDIR` — directory where generated quote images are written (created if missing).
- `PGHOST` / `PGPORT` / `PGDATABASE` / `PGUSER` / `PGPASSWORD` — standard `pg` env vars; `db/index.js` instantiates `new Pool()` with no explicit config, so it picks these up automatically. Must be set before `db/index.js` is first required (i.e. after `dotenv.config()` runs in `server.js`).
- `TRUST_PROXY` — hop count passed to Express's `trust proxy` setting (default `1`). Needed so `req.ip` reflects the real client (for rate limiting/bans) rather than a reverse proxy's address, in front of which this API normally sits in production.
- `RATE_LIMIT_WINDOW_MS` (default 15 min), `RATE_LIMIT_GENERAL_MAX` (default 300), `RATE_LIMIT_STRICT_MAX` (default 10), `RATE_LIMIT_STRIKE_LIMIT` (default 5), `RATE_LIMIT_STRIKE_WINDOW_MS` (default 1h), `RATE_LIMIT_BAN_DURATION_MS` (default 24h) — all tunable knobs for `lib/rateLimiter.js`, see Architecture below.
- The server listens on a hardcoded port `50000` (not configurable via env).
- `platform-integration/config.template` + `platform-integration/cfgloc` — the contract with whatever platform deploys this repo (currently the `male-niti` platform's `mn` script): `config.template` is this `.env` shape with values as `${PLATFORM_VAR}` placeholders, filled in via `envsubst` from the *platform's own* `.env` (now including `${ATODO_JWT_SECRET}` alongside the `DB_*` vars); `cfgloc` is a single line, the absolute in-container path (`/api/.env`) the rendered result gets bind-mounted to. Present because the platform's own `db` service name/credentials aren't knowable from inside this repo. A platform that doesn't provide this subfolder just runs the image with whatever `.env` was baked in at build time instead.

## Architecture

- `server.js` — loads `.env`, registers the two custom fonts, and mounts each router at its resource path (`/services`, `/pricing`, `/work`, `/blog`, `/contact`, `/v1/quotable`, `/v1/api-docs`, `/api-keys`, `/imprint`, `/feed.xml`, `/atodo/v1`, `/atodo/v1/api-docs`). No business logic here. Note `/v1/quotable` and `/v1/api-docs` were the only versioned paths before the A-To-Do integration added its own `/atodo/v1` prefix (required by that project's own `api-spec.yaml`) — still not the start of a versioning scheme applied to the CMS resources above.
- `routes/docs.js` serves Swagger UI (`swagger-ui-express`) at `/v1/api-docs`, rendering `api-spec.yaml` (parsed at request-router-setup time via `js-yaml`). **`api-spec.yaml` documents the full API** — every write endpoint, the `contact` admin endpoints, `/v1/quotable`, the `/api-keys` endpoints, and the `bearerAuth` security scheme. When adding or changing any endpoint, update this file in the same change — it's user-facing documentation, not just an artifact from the original design phase, and it'll silently drift otherwise.
- `routes/imprint.js` — a singleton resource (exactly one row, no `id` in the API surface): `GET /` is public and 404s until it's been created; `POST /` (super admin) creates it and 409s if one already exists; `PATCH /` (super admin) updates it and 404s if it doesn't exist yet. Existence is checked in application code, not a DB constraint.
- `routes/feed.js` — `GET /feed.xml` (mounted at the API's root path, not nested under a resource), a public RSS 2.0 feed built from `blog_posts` at request time (`?lang=en` for the English fields). Note the API spec documents this path under `https://maleniti.com` rather than the usual `/api`-prefixed server, since every page links it as a bare root-relative `feed.xml` per RSS convention — whatever proxies this API in front of the real domain needs its own route for it.
- `routes/services.js`, `routes/pricing.js`, `routes/work.js` are thin config objects passed to `lib/crudResource.js`, a factory that generates the full `GET /`, `POST /`, `PUT /:id`, `PATCH /:id`, `DELETE /:id` set for a table keyed by its `id` column. Add a new uniform resource by adding a table to `db/schema.sql` and a config file here — no route boilerplate needed. `PUT` re-validates all `required` fields (full replace semantics); `PATCH` requires none but 400s if the body has no updatable fields; `DELETE` and lookups 404 on a missing `id`. List responses now include `id` (previously omitted) since it's the handle needed for the other three methods.
- `routes/blog.js` doesn't use the factory — it's keyed by `slug` (not `id`), and the list endpoint returns summary columns (`limit`/`offset` query params, defaults 20/0) while `GET/PUT/PATCH /blog/:slug` return the full row including `body_hr`/`body_en`. Write logic is hand-rolled here but reuses `lib/buildSet.js` for the same "only touch columns present in the body" behavior as the factory.
- `lib/buildSet.js` — turns whichever whitelisted columns are present in `req.body` into a parameterized `SET`/`INSERT` column list; shared by `crudResource.js` and `blog.js` so partial-update semantics stay consistent across both.
- `db/index.js` — the single shared `pg` `Pool`; `db/schema.sql` has the `CREATE TABLE` statements for all six tables (`services`, `pricing_plans`, `work_items`, `blog_posts`, `imprint`, `contact_submissions`) plus the `pgcrypto` extension (used for `gen_random_uuid()` on contact submission ids). This file is the source of truth for the schema, but **this repo doesn't apply it itself** — whatever project composes this API together with a Postgres container is responsible for running it (e.g. mounting it into `/docker-entrypoint-initdb.d`). There's no migration tool, so schema changes mean hand-editing this file and re-applying manually. `slug` is `UNIQUE` on both `work_items` and `blog_posts`.
- `lib/asyncHandler.js` — wraps async route handlers so a rejected promise logs the error and responds `500` instead of crashing the process; a Postgres unique-violation (`error.code === '23505'`, e.g. a duplicate `slug`) instead responds `409` with the constraint detail. Used by every router to avoid repeating this in each handler.
- `routes/quotable.js` — the image-rendering endpoint, mounted at `/v1/quotable`. `POST /v1/quotable` takes `{ quote, author }`, measures and centers multi-line text on a 1920x1080 canvas, draws curly quote marks around the quote text, right-aligns the author lines (prefixing the first with `~`), and always responds with the generated PNG buffer directly (`res.send(buf)`) regardless of whether saving it to `MNAPI_OUTDIR` succeeds — the disk write is wrapped in its own `try/catch` and only logged on failure, so a permissions problem there doesn't break the response. There's no cleanup of successfully saved files — the output directory grows unbounded over time; this is expected given the current design, not a bug to silently "fix" without discussion.
- `lib/requestLogger.js` — mounted first in `server.js`, before `express.json()`, so its timer covers the full request lifecycle. Logs one line per request: `yyyy-MM-ddTHH:mm:ssZ (LVL): METHOD /path?query - STATUS - DURATION ms`, where `LVL` is `MSG` (2xx/3xx), `WRN` (4xx), or `ERR` (5xx) — always exactly 3 letters, matching the fixed `ERR`/`WRN`/`MSG`/`DBG` level enumeration (`DBG` isn't reachable from this access-log path).
- All bilingual content fields follow the API spec's `_hr`/`_en` sibling-field convention (Croatian/English) rather than nested locale objects — keep new columns/fields consistent with that shape.

## Auth, rate limiting, and IP bans

- Auth is a single Bearer API-key scheme, not sessions/JWT. `lib/authenticate.js` is mounted globally and **never rejects** — it just sets `req.auth` to `{ id, label, isSuperAdmin }` for a valid, non-revoked key (matched by SHA-256 hash against `api_keys.key_hash`) or `null` otherwise. Whether auth is actually required is entirely up to each route/middleware downstream.
  - `lib/requireSuperAdmin.js` — 401 if `req.auth` is null, 403 if it's set but not a super admin. Used on every mutating `services`/`pricing`/`work`/`blog` route and on `contact`'s `GET /` and `PATCH /:id`.
  - `routes/quotable.js` treats *any* valid key (super admin or not) as "authenticated" — that alone decides whether the generated image also gets written to `MNAPI_OUTDIR`; there's no `requireSuperAdmin` gate on this route at all, unauthenticated calls are still served, just not persisted.
  - Only the raw key's SHA-256 hash (`lib/apiKeyHash.js`) is ever stored or queried — issue new keys with `npm run create-api-key -- <label> [--admin]`, or `docker exec <container> node scripts/create-api-key.js <label> [--admin]` against a running container. The plaintext key is printed once at creation and is not recoverable; there's no "list/reveal key" endpoint by design. Revoke a key by setting its `revoked_at`.
  - `routes/apiKeys.js` — `GET /api-keys/me` returns the calling key's `{ id, label, is_super_admin }` (401 if unauthenticated); used to validate a key and to discover the id needed for self-rotation. `POST /api-keys/:id/rotate` replaces a key's secret in place (id/label/admin flag unchanged) and returns the new plaintext once, same as `create-api-key.js`. It's a mutating endpoint that isn't super-admin-gated: any authenticated caller may rotate their own key (`req.auth.id === :id`); rotating someone else's still requires `req.auth.isSuperAdmin`. 404 if the id doesn't exist, 409 if it's already revoked. `POST /api-keys/bootstrap` is the other exception, and the one endpoint in the whole API that's a mutating route with no auth check at all: it provisions the very first super admin key on a fresh deployment (the only bootstrap path besides shell access to run `create-api-key.js`), and is safe to leave public specifically because the `INSERT ... WHERE NOT EXISTS (...)` it runs is atomic — it 404s once any admin key already exists, and concurrent callers on an empty table can't both win. Anyone reaching this endpoint before the real operator does gets the admin key, so hit it yourself immediately after deploy, before the service is exposed publicly.
- `lib/ipBan.js` — `checkBanned` is mounted globally, first, before rate limiting or auth; it 403s any IP with a row in `banned_ips` whose `expires_at` is null or still in the future. `banIp(ip, reason, durationMs)` upserts a ban (`durationMs: null` = permanent). Because it queries Postgres on every request, a request only ever reaches `/v1/api-docs` or any other DB-independent route if the database is actually reachable — a DB outage takes the whole API down, not just data endpoints.
- `lib/rateLimiter.js` exports two `express-rate-limit` instances built from the env vars above: `general` (mounted globally) and `strict` (mounted only on `POST /contact` and `POST /v1/quotable` — the spam/CPU-cost-sensitive ones). Both share one in-memory "strikes" counter keyed by IP: each individual rate-limit violation (from either limiter) adds a strike, and hitting `RATE_LIMIT_STRIKE_LIMIT` strikes within `RATE_LIMIT_STRIKE_WINDOW_MS` auto-bans the IP for `RATE_LIMIT_BAN_DURATION_MS` via `banIp`. The super admin (`req.auth.isSuperAdmin`) is exempt from both limiters entirely, so routine admin work can't trip a ban.
  - The strikes Map is in-memory and resets on restart — acceptable since it's just the on-ramp to a ban, and the ban itself (in Postgres) is what's meant to persist.
  - To test rate limiting/banning quickly without waiting out the real windows, override the `RATE_LIMIT_*` env vars on a disposable container, e.g. `docker run --rm -e RATE_LIMIT_STRICT_MAX=2 -e RATE_LIMIT_STRIKE_LIMIT=2 -e RATE_LIMIT_STRIKE_WINDOW_MS=600000 -e RATE_LIMIT_BAN_DURATION_MS=10000 --network your-network -p 50001:50000 mnapi` — don't lower the real defaults to test them.

## A-To-Do integration (`/atodo/v1`)

A complete, independent backend for the separate `atodo` client project (a sibling repo, not part of this one), implementing `atodo-api-spec.yaml` (copied from `../atodo/api-spec.yaml` — keep it in sync by hand; there's no automated link between the two repos, so if that spec changes, re-copy it here and update `routes/atodo/` to match). Deliberately kept isolated from the CMS routes above — separate auth scheme, separate tables, separate router tree under `routes/atodo/` — rather than threaded through the existing `lib/authenticate.js`/`crudResource.js`/etc., since the two APIs share nothing except the Postgres instance and Express app.

- **Auth**: per-account bearer JWTs, not the CMS's API keys. `lib/atodo/jwt.js` is a hand-rolled HS256 JWT (sign/verify via Node's own `crypto.createHmac`, base64url-encoded) — deliberately not the `jsonwebtoken` package, to avoid a new dependency for a format this small. Signed with `ATODO_JWT_SECRET` (see Configuration). `lib/atodo/authenticate.js` (`requireAtodoAuth`) is the opposite of the CMS's `lib/authenticate.js`: it verifies the bearer token and, unlike the CMS version, **rejects with 401 outright** if it's missing/invalid, since `atodo-api-spec.yaml` declares `bearerAuth` as a global security requirement (routes opt out with `security: []`, not the other way around). Applied per-sub-router in `routes/atodo/index.js` to everything except `/auth/register`, `/auth/verify-email`, and `/auth/login`; `GET /auth/me` guards itself individually since it's the one route in `routes/atodo/auth.js` that needs auth alongside three that don't.
  - `requireAtodoAuth` is the one place the "tokens are a snapshot, not live truth" rule below doesn't hold: it hits `atodo.accounts` on every single authenticated request (not just `/auth/me`) to check the token's `pwv` claim against the account's live `password_changed_at`, rejecting with 401 on any mismatch — the mechanism `POST /users/me/change-password` relies on to actually end every *other* outstanding session immediately, since a self-contained JWT can't invalidate itself otherwise. Worth the extra query given what it buys; don't revert it back to a pure-stateless check without another way to satisfy that requirement.
- **Passwords**: `lib/atodo/password.js` hashes with Node's built-in `crypto.scryptSync` (salt:hash hex, `crypto.timingSafeEqual` for comparison) — no `bcrypt`, again to avoid a new (and in bcrypt's case, native-build) dependency alongside `canvas`.
- **Tokens embed a subscription snapshot (and a password version)**: `lib/atodo/token.js`'s `issueToken`/`toUser` build the `Token`/`User`/`Subscription` shapes `atodo-api-spec.yaml` documents from an `atodo.accounts` row — re-issued (fresh `token` in the response) by every endpoint that changes what it claims, per the spec's own description of `Token`. `issueToken` also embeds `pwv` (the account's `password_changed_at`, or `null` if it's never been changed) — not part of the documented `Token` schema (it's an internal enforcement detail, not something the client is meant to read), but checked by `requireAtodoAuth` on every request, see above.
- **`POST /users/me/change-password`** (`routes/atodo/users.js`): requires `currentPassword` (401 `INVALID_CREDENTIALS` if it doesn't match) alongside a `newPassword` of at least 8 characters (400 `INVALID_PASSWORD` otherwise), then bumps `password_changed_at` — which, via the `requireAtodoAuth` check above, invalidates every token issued before this call, including the one authenticating this very request. The response's freshly-issued token (built from the just-updated row) is the only one that keeps working, so the caller stays logged in on this session while every other one is kicked.
- **Lifecycle deletion**: `lib/atodo/lifecycle.js`'s `enforceLifecycleDeletion` implements the spec's 12-month-inactivity and scheduled-deletion (`POST /users/me/schedule-deletion`) policies — checked lazily at `POST /auth/login` and `GET /auth/me` (no background job), matching the spec's own notes on those two endpoints.
- **Mocked Stripe**: `lib/atodo/stripe.js`'s `createMockCheckoutSession` never calls the real Stripe API — payment always "succeeds" immediately (no pending state), and `routes/atodo/subscriptions.js` activates the Pro subscription server-side right when the checkout session is created rather than waiting on a webhook. The returned `checkoutUrl` redirects straight to the caller's `successUrl` with a `session_id` param appended, the same way Stripe's own hosted page would on a real completed payment — so the existing `atodo` client's `checkout.html` polling flow (`GET /subscriptions/checkout-sessions/{sessionId}`) works unmodified against the mock.
- **Mocked email**: `lib/atodo/mailer.js`'s `sendEmail` just `console.log`s the message (prefixed `[atodo mail]`) and always resolves — used for the registration verification link in `routes/atodo/auth.js`. No real provider is wired up.
- **Tables** (`db/atodo-schema.sql`, applied the same way as `db/schema.sql` — see Commands): a dedicated `atodo` Postgres schema (`CREATE SCHEMA IF NOT EXISTS atodo`), not just a table-name prefix, keeping every reference schema-qualified (`atodo.accounts`, not `atodo_accounts`) in `routes/atodo/`/`lib/atodo/`. `atodo.pending_registrations` (unverified registrations, promoted into `atodo.accounts` by `POST /auth/verify-email` and deleted either way), `atodo.accounts` (one row per verified account; subscription state is columns on this table, not a separate one, since an account has at most one subscription at a time — `subscription_plan IS NULL` means "Free"; `password_changed_at` backs `POST /users/me/change-password`'s token invalidation, see above), `atodo.tasks` (keyed `(account_id, id)`, bulk-replaced by `PUT /tasks`; date-only fields are `TEXT`, not `DATE`, matching the spec's own "plain `YYYY-MM-DD`, compared as strings" contract and sidestepping `node-pg`'s timezone-sensitive `DATE`→`Date` conversion), `atodo.checkout_sessions` (mock Stripe sessions, always inserted already `status = 'paid'`).
  - `CREATE TABLE IF NOT EXISTS` is a no-op against an already-deployed table, so a column added to an existing table (like `password_changed_at`) needs its own idempotent `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` right after the `CREATE TABLE` block to actually reach a deployment that already ran an earlier version of this file — there's still no real migration tool (see Commands), this is just the pattern for column-only additions going forward.
- **Rate limiting**: `POST /auth/register` and `POST /auth/login` use `rateLimiter.strict` (see "Auth, rate limiting, and IP bans" above) — public, credential-guessing/spam-sensitive, same reasoning as `POST /contact`/`POST /v1/quotable`.
- **Docs**: `routes/atodo/docs.js` serves a second, separate Swagger UI at `/atodo/v1/api-docs` for `atodo-api-spec.yaml` — kept separate from `/v1/api-docs` rather than merged into one spec, since both specs declare a `bearerAuth` scheme that means something different (CMS API key vs. atodo account JWT).
- `db/index.js` also exports `getClient()` (a raw `pool.connect()`) alongside `query()`, added for `PUT /tasks`' bulk replace, which needs a transaction (`BEGIN`/delete-all/insert-each/`COMMIT`, with `ROLLBACK` + `client.release()` on error) — the CMS routes only ever needed single statements via `query()`.

## Known gap

If the bind-mounted `MNAPI_OUTDIR` host directory is owned by `root` (e.g. Docker auto-created it on first `docker run`), writes from the non-root `appuser` inside the container will fail with `EACCES`. Fix by `chown`-ing the host directory to match the container's `appuser` uid, or by removing the directory before the first run so Docker/the app can create it with the right owner.
